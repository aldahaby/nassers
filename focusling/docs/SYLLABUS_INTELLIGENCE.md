# Syllabus Intelligence (parser 3.0: academic reading)

Studyling reads a syllabus **on the device** and turns it into something the student reviews:
course details, deadlines, grading and weekly structure. Nothing is planned until the student
approves it. Everything is deterministic rules: **no AI model or backend is connected.**

```
file ──► core/documents (type check, DOCX, size/zip-bomb limits, readability)
     ──► stripRunningHeaders (repeated headers/footers, page numbers)
     ──► syllabusParser (deadlines: dates, times, release vs due, tentative, exam periods,
                        conflicts, recurrence, weights, stated time zones, explicit coverage)
     ──► syllabusInsights (course identity, people, office hours, class times, grading,
                           weekly topics, "X covers Weeks 1–5", key dates, policy headings)
     ──► academicReading (named assessments from headings/grading rows, their own sections:
                          requirements, submission, coverage; conditional deadlines;
                          year evidence; dated lecture list)
     ──► import draft (catalog merged over parser lines, year placement, trust status per
                       item, revision matching, course-detail diffs)
     ──► student review ──► commit (planner schema 3) ──► Planner, Lock-In, Stats, Journey
```

## What it reads (and where)

| Format | Web preview | iPhone app |
|---|---|---|
| Plain text / pasted text | ✅ | ✅ |
| DOCX | ✅ (pure TypeScript ZIP + DEFLATE reader, `core/documents`) | ✅ (same code) |
| Text-based PDF | ✅ Mozilla PDF.js in the browser (iPhone Safari included; **not yet run on a physical iPhone**, see `docs/IPHONE_SAFARI_PDF_TEST.md`) | PDFKit (`modules/studyling-native`), **not yet run on a device** |
| Scanned PDF | ❌ said plainly: "This PDF is a scan…" (no OCR in the browser) | Vision OCR per page, **not yet run on a device** |
| Photo of a page (JPEG/PNG/HEIC) | ❌ | Vision OCR (`extractImageText`), **not yet run on a device** |
| Legacy .doc, other files | ❌ "can't be read here" | ❌ |

- The type is decided from the file's bytes, not its name.
- Files over 15 MB are refused. DOCX archives have entry, size and compression-ratio limits, and
  encrypted files are refused.
- DOCX: only `word/document.xml` is read. Headers, footers, comments, macros and embedded
  objects are never read or run. Tables become `cell | cell` rows, and page breaks are kept.
- Text that is mostly unreadable (for example a bad scan) is **refused** with a clear message,
  rather than imported in part.
- Multi-column PDFs:
  - **Web:** `core/documents/pdfLayout.ts` rebuilds each page from PDF.js text fragments.
    Lines stay left to right, table columns stay aligned, row gaps become blank lines, and
    two-column prose is read one column at a time (tables are left alone).
  - **iOS:** PDFKit's order is used, so columns may still interleave there.

### PDFs on the web (PDF.js)

- **Engine:** `vendor/pdfjs/pdfjs.web.js`, generated by `node tools/vendor-pdfjs.mjs` from
  `pdfjs-dist` 6.3.289 (legacy build, which carries polyfills for older Safari).
  - It's pre-bundled because Metro can't bundle pdf.js as shipped (`import.meta.url` and
    dynamic `import()` of variable paths).
  - The worker runs on the main thread, so there's no separate worker file. This works in the
    normal web build and the single-file preview alike.
  - It's loaded only on web (`services/documents/pdfEngine.web.ts`); native builds don't
    include it.
- **Reading:** `services/documents/pdfReader.ts` reads each page's text layer and keeps the page
  number of every line.
  - A page with no text but with an image is reported as skipped ("Page 2 couldn't be read").
    A blank page is just empty.
  - A PDF where every page is a picture fails with `scanned`.
  - A password-protected PDF fails with `encrypted`.
  - A damaged file fails with `unreadable`.
  - More than 80 pages fails with `tooLarge` (`DOCUMENT_LIMITS.maxPdfPages`).
  - Nothing is uploaded.
- **Wrapped lines:** a date or time cut onto the next line ("…due Friday, January 22, 2027 at" /
  "11:59 PM.") is joined back (`joinWrappedTimes`); the emptied line keeps its place.
- **Tests:**
  - `core/__tests__/documents/pdfLayout.test.ts`;
  - `services/__tests__/pdfRead.test.ts` (real PDFs in `core/__tests__/fixtures/pdf/`: tables,
    two-column, the BIOL layout, scanned, mixed, blank page, encrypted, corrupt;
    regenerate with `tools/pdf-fixtures/make.mjs`);
  - browser suite m18;
  - the real BIOL 115 PDF, local only.

## What it extracts (only when the syllabus states it)

| Area | Details |
|---|---|
| Course identity | Institution, code, title, term/year, section |
| People | Instructor(s) and TAs from labelled lines. Email only where written, and saved only if the student opts in |
| Times | Office hours (who, days, times, place) and class meetings (lecture/lab/tutorial, compact codes like MWF/TTh) |
| Deadlines | Assignments, quizzes, exams, papers, projects, labs, readings, presentations, with time, release date and weight on the line |
| Grading | Components and weights, including "8 × 4%". The total is checked, and a total that isn't 100% is shown, never "fixed" |
| Structure | Weekly topics and readings, explicit coverage ("Midterm covers Weeks 1–7", "Midterm (Chapters 1–4)") linked to those weeks' topics |
| Key dates | Drop/withdraw deadlines and no-class days are saved with the course, never as tasks |
| Policies | Headings only (e.g. "Late Work Policy"), with page. No policy text is stored |

## Date reasoning

- **Release vs due:** "released Aug 31, due Sept 11" sets the due date and records the release.
- **Missing year:** inferred from the term ("Fall 2026" → 2026, with January after a fall term
  going to the next year). Each inference is recorded and shown, e.g. "Year 2026 from
  “Fall 2026”" (status **Inferred from context**).
- **Tentative** dates ("tentative", "subject to change") need review.
- **Exam periods** ("during the final exam period, Dec 8–17") become a **window**, never a date.
  The assignment is saved as an unresolved requirement until the student adds the date.
- **TBA** dates ("date to be announced") are saved as unresolved requirements with no date.
- **Conflicts:** two dates for one item are both shown, and the student picks one.
- **Time zones:** "11:59 PM ET" is recorded. A zone that differs from the course zone is flagged
  for review.
- **Weekly activities** (tutorials every Thursday) are class meetings, not assignments.

## Academic reading (parser 3.0)

Layout handling learned from the real BIOL 115 text:
- PDF lecture tables ("3-Sep Thurs Lect.1 …"), read block by block with the topic and
  assignments columns separated;
- people listed in columns;
- wrapped sentences joined back together;
- deadline evidence ranked ("Deadline:" over a date in a sentence over a bare date; approvals,
  citations and "published since" cut-offs ignored);
- short names ("LitA" for "Literature assignment A");
- per-item late rules, and where to find your assigned lecture;
- the lecture schedule's weekdays as year evidence, with the year most dates fit suggested (the
  student still chooses).

Rebuilt after a real syllabus (McGill BIOL 115) was badly misread: wrong course code (the
BIOL 112 prerequisite), no instructors, no class times, sentence fragments as titles ("uploaded to
myCourses Assignment 3 tab"), only some items, and the year silently defaulted.

- **Course identity:** prerequisite/restriction lines are never the course; when several codes
  appear, the most frequent heading code wins. Credits are read ("3 credits").
- **People and class times** are read under headings ("Instructors", "Class schedule") as well as
  from labels, including several names on one label. Location comes from the same or next line.
- **Named assessments** (`buildCatalog`): headings and grading rows ("Assignment 3: Literature
  Assignment A (15%)", "Final examination | 50% | TBA") define items. Each item owns the lines
  below its heading until the next heading. Lines elsewhere that name it ("The midterm will be
  written on…") add dates. Titles are "Assignment 3 — Literature Assignment A", never a sentence.
  Category rows ("Homework (8 x 4%)") are groups, not items.
- **Conditional deadlines:** "due three days before your assigned lecture" is saved as a rule with
  no date. Review asks "Which lecture were you assigned?". The answer can be picked from the
  syllabus's lecture list or given as a date, and the deadline is then worked out. A rule is never
  turned into a fake fixed date.
- **Years:** evidence comes from the heading, explicitly written years, and weekday + date pairs
  ("Thursday, October 29" is a Thursday only in 2026). When the evidence disagrees, nothing that
  depends on the year gets a date until the student answers "Which year is this course?" (with
  the evidence one tap away). Dates written with a year that disagrees become a choice. After the
  answer, any weekday that doesn't match is flagged ("The syllabus says Tuesday, but October 20,
  2025 is a Monday"). A student's own date edit is never moved by a year answer.
- **Weights** that are missing are never filled in. A grading list that doesn't reach 100% is
  explained ("adds up to 70%… Final Exam has no weight in the syllabus").

## Trust statuses (no fake percentages)

| Status | Meaning |
|---|---|
| Confirmed by you | The student edited or confirmed it |
| From your syllabus | Stated in the syllabus (no badge shown in the date list) |
| Worked out from context | Worked out (e.g. the year), with the note shown |
| Worth a quick check | Ambiguous, tentative, time zone, OCR damage… (the reason is shown in words) |
| Syllabus disagrees | The syllabus gives two different values |
| No date yet | The syllabus doesn't say (TBA, exam period only, conditional) |

Each item shows its source page and line. During review it also shows the original line as a
quote; that quote is held in memory only and never saved.

## Review → planner (Milestone 17: three stages)

1. **Your course at a glance:**
   - code, title, term, credits and institution;
   - instructors, and class times with the room;
   - counts (assessments, with a date, waiting for a date);
   - one line saying how many things there are to check.
   Course details and policies are under "More about this course".
2. **Just a few things to check:** only questions that change a date. Each card resolves on its
   own, and "Skip for now" leaves the item undated. The questions:
   - which year;
   - which lecture;
   - which of two dates (each option says where it comes from);
   - the date of an exam-period exam;
   - an item with no date;
   - a weekday that doesn't match;
   - skipped PDF pages.
   Informational notes (grading below 100%, lecture weekdays that don't fit the chosen year)
   sit under the questions.
3. **Ready for your planner:** items split into "With a date (they can get study blocks and
   reminders)" and "Waiting for a date". Each item expands to what to do, how to submit, the
   late rule and your estimate. "Change title, type or date" and "Source details" (page,
   inferences, reasons) are collapsed. **Add N items** saves exactly N.

After import, the planner offers **Plan a study session** (`planner/plan`):
- pick a dated assessment;
- give your own estimate;
- see blocks labelled "Suggested by Studyling · not a course requirement";
- accept, suggest again, or skip.

Earlier version (Milestone 16) of the review, kept for reference:

1. **Course overview:** name, code, credits, term, institution, instructors, class times and
   location, grading. "More course details" opens the rest (section, office hours, lectures,
   policies with their summaries, email toggle).
2. **Needs your attention:** only real questions (which year, which lecture, which of two dates,
   an item with no date, a weekday that doesn't match, a grading list that doesn't add up), each
   with its answer controls right there.
3. **Important dates:** every item sorted by date, undated ones last with the reason in words.
   Tapping an item shows what to do, how to submit, coverage, notes, the page it came from, and
   the editors.
4. **"Review & add to planner"** opens a confirm step listing exactly what will be added. The
   button says "Add N items", and N is the number saved. Items without a date are saved as
   requirements and never planned or reminded until they have one.

Import diagnostics (parser version, header lines ignored, year evidence, per-item reasons) are
shown only when Developer tools are on.

- The student can edit the course details (institution, section), choose whether to save them,
  and choose whether to include email addresses (off by default).
- Each item can be edited, confirmed, excluded or have a conflict resolved, and grading,
  structure and key dates can be reviewed. "Cancel import" changes nothing.
- On commit:
  - Assignments keep their provenance, weight, release date, exam window, coverage and inference
    notes.
  - The course keeps its `details`.
  - Lecture times fill `meetingSchedule` if that was empty.
- **Three kinds of things stay distinct in the UI:**
  - course requirements ("Course requirement · from your syllabus");
  - Studyling's suggestions (study blocks, and the exam "Suggestion from Studyling · not from
    your instructor" card);
  - the student's own tasks ("Added by you").
- No tasks are created automatically and no study length is assumed. Planning still needs the
  student's own estimate.

## Revised syllabi

Re-importing the same file is a no-op (same content hash and parser version). A revised syllabus
shows the following before anything changes:

- **Items:** new, changed (old → new), unchanged, and no longer listed (kept by default; the
  student chooses).
- **Possible matches:** a new item that looks like a removed one is offered as "Is this the same
  as …?". This triggers on title similarity, or on the same type plus the same leading word plus
  a due date within 14 days (`REVISION_MATCH`). "Same item" updates the existing assignment, so
  study history is kept and no duplicate is created. "Different" keeps both. Nothing is merged
  silently.
- **Course details:** grading weight changes, added or removed components, weekly topic changes,
  and people or class-time changes.
- **The student's edits win.** A source change to an edited field becomes a visible conflict
  (`applySourceUpdate`).

## Lock-In, Stats, Journey, pets

- "Start & Lock now" on an assignment starts the existing focus session with the course and
  assignment attached. The running session shows "Studying: CS 1301 · Homework 2".
- The finished session is one `StudySession` record. Stats counts it once, capped to real elapsed
  time, under its course. An assignment's "Studied" minutes use the same rule.
- Studying never completes a task. Only "Mark as done" does.
- New Journey milestones (each stored once):
  - "First syllabus task completed";
  - "First Lock-In for a specific task";
  - "Started preparing for an exam".

  "Imported your first syllabus" already existed. Repeated imports never re-award.
- **Pets:** importing gives no coins or XP. Rewards still come only from focus sessions and
  missions.

## Course Spaces (future, data only)

`courseSpaceKeyOf(identity)` gives `institution/term/code`, plus an optional section. It is null
unless all three parts are known, and it always includes the institution, so the same code at two
universities never matches. Nothing is published, shared or joined.

## AI architecture

`services.syllabusAnalysis` is the `LocalSyllabusAnalysisProvider` (on device).
`UnavailableRemoteSyllabusAnalysisProvider` documents the future boundary: it refuses without
explicit consent and is unavailable without a backend. A real remote model needs:

- a Studyling backend that holds the model key (never the app);
- a per-import disclosure screen;
- no retention by default;
- results going through the same review.

No mock AI output is ever shown as real.

## Limitations

- **BIOL 115 regression:** the real syllabus text a student imported passes the acceptance suite
  (`core/__tests__/planner/biol115.test.ts`, browser suite m17). The real text is copyrighted
  course material, so it lives only in the git-ignored `fixtures/private/` folder and that part
  of the suite runs only where the file exists. `BIOL115_LAYOUT` (committed, our own wording)
  reproduces its layout traps in every run:
  - a title-case code after the title, and a restriction wrapped onto a line that starts with
    another course code;
  - names under "Instructors' information", and TAs side by side;
  - a PDF lecture table with topics wrapped around the date;
  - weights on "Value:" lines;
  - "published since" and citation dates;
  - exams described only in prose.
- That syllabus's grading summary table was an image, so the midterm and final weights aren't in
  the text. Studyling says so instead of guessing.

- PDF, scanned PDF and photo reading are iOS-only and have **not been run on a device**.
- Rules recognise common English layouts (US/Canadian). Unusual layouts, non-English syllabi and
  multi-column PDFs can miss items; review is always required.
- People, office hours and grading are read from labelled lines and grading sections. Free-form
  prose may be missed and is then shown as "Not specified".
- Exam coverage is linked only when written explicitly.
